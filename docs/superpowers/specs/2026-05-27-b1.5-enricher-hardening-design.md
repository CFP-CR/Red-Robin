**Date:** 2026-05-27
**Branch:** `wm/enricher` (off `dev-juan`)
**Status:** Approved (brainstorm) — ready for `/writing-plans`

## 1. Context & Goal

Plan B1 built the `WorkingMemoryEnricher` (an async bus consumer that turns beacon command output into Working-Memory facts via a Haiku-class LLM, publishing `working_memory.deltas` events the reducer merges single-writer). B1 is CI-green and proved the thesis in a live-beacon smoke (#149 host enrichment works; #145 no kerberos FP at the enricher; plaintext cred captured **when the output carried context**). But the smoke surfaced **five production-readiness gaps**. B1.5 fixes them so **B1 + B1.5 merge together as one production-grade PR** (operator-approved: do NOT merge B1 alone — a routine `dir /s` 429-storms it).

This feature has no prior spec (the gaps emerged from the smoke); this document is it.

## 2. Scope

**IN — B1.5, one coordinated PR on `wm/enricher`:**
1. **command-recovery** — give the enricher the command that produced each output (exact, via the CS `$5` correlation id). Includes a small `.cna` + event-schema change.
2. **concurrency / 429 control** — bound the enricher's parallel LLM calls.
3. **auto-observation filter** — stop the enricher from enriching Red Robin's own console annotations (enricher-side, defensive).
4. **junk-host grounding** — OS-agnostic prompt grounding so usernames / paths / drive labels aren't extracted as hosts.
5. **findings dedup** — collapse duplicate findings in the merge.

**OUT — separate plans:**
- **`.cna` root of auto-observation** (stop `blog`-ing Red Robin's annotation into the beacon output stream) → the `.cna` plan.
- **Re-emission on reconnect / `source_event_id` (#152)** → the `.cna` plan.
- **B2** — retire the regex (`_NTLM_LINE`/`_HOSTNAME_LINE`/`_KERBEROS_TICKET`/`_on_beacon_command_output`) + orphaned `upsert_host`/`upsert_credential` + tier-3 `doctor` counters.
- **Scale tiers (future):** Message Batches API, Tier-2 upgrade, proactive `anthropic-ratelimit-*` header throttling.

## 3. Empirical grounding — CS hook args (verified live 2026-05-27)

Verified with a throwaway spike (`adapters/cobaltstrike/spike/redrobin_hook_debug.cna`, console-only) on CS 4.x. **The official Aggressor events doc is incomplete** — it omits the per-command correlation id. Real args:

| Hook | $1 | $2 | $3 | $4 | $5 |
|---|---|---|---|---|---|
| `beacon_input` | bid | operator | **full command** (`shell systeminfo`) | timestamp(ms) | **correlation_id** (hex) |
| `beacon_tasked` | bid | task description | timestamp | — | **correlation_id** |
| `beacon_output` | bid | output text | timestamp | **job id** (30,31,…) | **correlation_id** |

**Key facts (proven):**
- **`$5` is a per-command correlation id** — identical across `beacon_input`/`beacon_tasked`/`beacon_output` of one command, unique per command.
- **It survives rapid-fire.** A `sleep 10` + queued trio produced the real interleave `input(A,$5=18ff)` → `input(B,$5=272d)` → `output($5=18ff)` → `output($5=272d)`. Each output carried **its own** command's `$5` — the exact case where a "bid + last-command" heuristic mis-attributes, but `$5` does not.
- **Big output = ONE `beacon_output` event** (systeminfo ~3KB came in a single event — no multi-chunk at the hook level).
- **No-output command = no `beacon_output`** (`cd C:\` fired input/tasked only).
- `beacon_output.$4` = the job id (so the `.cna`'s existing `task_id=$4` is the job id, not empty).
- The gate is **fail-open** (commands executed with the daemon down) — noted, out of scope.

## 4. Area 1 — command-recovery (exact via `$5`)

**Problem:** the wire `beacon.command_output` event has no `command` field, so the enricher receives `command=""`. Consequences: the denylist is inert (every ≥8-char output is enriched) and bare outputs are under-extracted (a clean `admin:P@ssw0rd` was MISSED; the same with the in-output hint `"These are my creds:"` was captured — proving **context is the missing piece**).

**Design — exact correlation via the `$5` id:**
- **`.cna`** (`adapters/cobaltstrike/redrobin.cna`): forward `correlation_id = $5` on BOTH emits.
  - `on beacon_input { … redrobin_emit_command_input($1, $2, $command, $3, $5); }` → add `"correlation_id"` to the JSON.
  - the `beacon_output` hook → `redrobin_emit_command_output($1, $task_id, $2, $5)` → add `"correlation_id"`.
  - Small, additive, no gate-logic change. **Smoke-verified** (no CI for `.cna`).
- **Schema** (`protocol/schemas/v0.1/events/beacon_command_input.schema.json` + `beacon_command_output.schema.json`): add optional `"correlation_id": {"type":"string"}` (keep `additionalProperties:false`).
- **Domain** (`redrobin/domain/events.py`): add `correlation_id: str | None = None` to both event models.
- **Enricher** (`redrobin/application/enrichment/enricher.py`): on `beacon.command_input`, cache `correlation_id → raw command` (bounded dict). On `beacon.command_output`, look up the command by `correlation_id` (exact). **Fallback:** if `correlation_id` is absent/null (older CS, or input not yet seen), fall back to a per-`bid` last-command cache, then to `""` (current degraded behavior). The recovered command feeds `should_enrich` (denylist works) and the LLM context.

**Why exact, not the heuristic:** the rapid-fire proof (§3) shows `$5` correlates correctly where last-command mis-attributes. Operator decision: exactness over a best-effort heuristic, accepting the tiny `.cna` change.

**Cache bounds:** one entry per in-flight `correlation_id`; evict on lookup (pop after the matching output) + a max-size cap (e.g. 256) to bound a pathological no-output backlog. The `bid` fallback cache is one entry per beacon.

## 5. Area 2 — concurrency / 429 control

**Problem:** `dir /s C:\Windows` → hundreds of chunks → `asyncio.gather(*all)` fired them all at once → blew Tier-1 limits (50 RPM + 50K ITPM) → total enrichment failure + budget starvation.

**Design (official-doc-backed, multi-layer — none alone suffices):**
1. **Bounded concurrency:** a single **`asyncio.Semaphore(N)`** (shared across all enrichments, not per-command) wrapping each `llm.extract` call. `N` configurable via `enrichment_max_concurrency` (default **4**). Prevents the instantaneous fan-out storm.
2. **Backoff + jitter + `retry-after`:** the **Anthropic SDK already does this** (`max_retries`, respects the `retry-after` header Anthropic returns on every 429). We rely on it; keep/tune `max_retries` on `AnthropicEnricherClient`. No custom backoff (single source of truth).
3. **Prompt caching (already in place):** per the official docs, **cached input tokens do NOT count toward ITPM** for Haiku 4.5 — only uncached `input_tokens` + `cache_creation`. Our static system prompt is an ephemeral-1h cached block → per-call ITPM ≈ just the command output. This is the throughput multiplier.
4. **No info dropped:** large outputs serialize through the semaphore (throttle, slower) — chunking is unchanged; nothing is truncated. Optional: a structured **log warning** if a single output exceeds a high chunk count (no hard cap).

**Scale tiers (documented, not implemented in B1.5):** proactive throttle via `anthropic-ratelimit-*-remaining` headers; Tier-2 upgrade (50→1,000 RPM); Message Batches API (50% cheaper, async — too high-latency for near-real-time WM).

**Config:** `enrichment_max_concurrency: int = 4` (validated ≥1).

## 6. Area 3 — auto-observation filter (enricher-side, defensive)

**Problem:** Red Robin's own console annotation (`[Red Robin] novel pattern — Layer B reviewing async`, emitted by `redrobin.cna:241` `blog(...)`) leaks into beacon output and gets enriched into junk findings (`novel_pattern`/`unusual_activity`/`red_team_activity`) and "Red Robin" extracted as a `tool_used`.

**Design:** before enriching, **strip lines matching the self-annotation prefix** (`^\s*\[Red Robin\]`, prefix configurable) from the output. If the post-strip output is empty/below `min_output_chars`, **skip enrichment entirely** (no LLM call). Examples:
```
"[Red Robin] novel…\njcsp\jcspi"   → strip → "jcsp\jcspi"            (enrich)
"[Red Robin] novel…"                → strip → ""        → SKIP        (no junk finding)
"Host Name: JCSP\n[Red Robin] novel…\nDomain: WORKGROUP" → "Host Name: JCSP\nDomain: WORKGROUP" (enrich)
```
This is **defensive** (enricher-side). The **root fix** (stop the `.cna` from `blog`-ing into the output stream) is the separate `.cna` plan. A pure helper `strip_self_annotations(output, *, prefix) -> str` in the enrichment package; config `enrichment_self_annotation_prefix: str = "[Red Robin]"`.

## 7. Area 4 — junk-host grounding (OS-agnostic)

**Problem:** `WINDOWS` (from "Volume in drive C is Windows") and `JCSPI` (a username) were extracted as hosts.

**Design:** strengthen the enricher `_SYSTEM_PROMPT` (`AnthropicEnricherClient`) with an **OS-agnostic** grounding rule defining the *concept* of a host:
> A `host` is a distinct machine/system identity (hostname, FQDN, or IP). It is NOT a username, a file/directory path, a drive/volume label, a service name, or a generic word. Examples of NOT-a-host (any OS): `jcspi` (user), `Windows`/`C:` (drive/label), `web-svc` (service), `/etc/passwd` (path).

Prompt-grounding is the **general, production-grade** approach (it teaches the *concept*, which generalizes across Windows/Linux/macOS/cloud) — explicitly NOT a hardcoded stoplist (brittle + OS-specific = the opposite of general). **command-recovery (§4)** reinforces it: knowing the command was `dir`/`ls`/`cat` (not host-discovery) reduces spurious extraction. **Optional safety net (general, not OS-specific):** a minimal structural reject of empty/path-like host names in `apply_deltas` — added only if smoke shows residual junk.

## 8. Area 5 — findings dedup (no routine cap)

**Problem:** the WM `findings` array grew to ~52, mostly **duplicates** (re-emission + inert denylist + append-only with no dedup).

**Design:** in `WorkingMemoryRepo.apply_deltas`, **dedup findings by content** — key `(kind, summary, source_beacon_id)`. Skip a finding already present. **No routine cap** — findings are loot; keep all unique ones (the operator rejected dropping info). Optional: a very high safety ceiling (e.g. a few thousand) that only guards a pathological runaway, never trims normal use. (The **input/output to enrich is never capped → chunked**, unchanged — distinct from this.)

## 9. Architecture & data flow

The enricher's `run()` loop gains a `beacon.command_input` branch (cache `correlation_id → raw`), alongside the existing `beacon.command_output` branch. The output path becomes:
```
beacon.command_output(payload)
  → recover command (correlation_id lookup → bid fallback → "")
  → strip_self_annotations(output)             [Area 3]
  → should_enrich(command, output, …)           [denylist now works — Area 1]
  → chunk_output(output)                         [unchanged]
  → for each chunk: async with semaphore: llm.extract(...)   [Area 2]
  → parse_deltas → merge → publish working_memory.deltas
reducer.apply_deltas(deltas)
  → merge hosts/creds/tools (dedup by key, unchanged)
  → findings: dedup by (kind, summary, source_beacon_id)   [Area 5]
```
Single-writer invariant unchanged (enricher publishes; reducer writes). Junk-host grounding (Area 4) lives in the LLM prompt.

## 10. Testing

- **Unit (pure):** `strip_self_annotations` (3 cases incl. skip-if-empty); the correlation cache (exact match, bid fallback, no-command degraded); `should_enrich` with a recovered denylisted command (now skips); dedup in `apply_deltas`.
- **Integration (stub LLM + EventBus):** publish `command_input` then `command_output` with the same `correlation_id` → enricher enriches with the recovered command; rapid-fire (two inputs then two outputs, interleaved) → each output uses its own command; semaphore bounds concurrency (a counting stub asserts ≤ N in flight); the `[Red Robin]`-only output → no deltas, no LLM call; dedup → repeated identical finding stored once.
- **`.cna` + schema:** schema fixtures updated (optional `correlation_id`); the `.cna` change is **smoke-only** (no CI) — operator live-beacon smoke is its gate.
- **Real CI gates** (unchanged): `ruff check` / `ruff format --check` / `mypy redrobin/domain redrobin/application` / `lint-imports --config importlinter.cfg` / `pytest`.

## 12. Risks & open items

- **`$5` is undocumented** → could change across CS versions. Mitigated by the `bid`-last-command fallback when `correlation_id` is absent (graceful degrade, never a crash).
- **`.cna` is smoke-only** (no CI) → the `$5`-forwarding is verified live, treated with care (additive, reversible); the working gate is otherwise untouched.
- **Semaphore vs sustained rate:** `N=4` + SDK `retry-after` self-throttles to the rate ceiling; a proactive header-based limiter is deferred (scale tier).
- **Auto-obs filter is defensive** — the `[Red Robin]` annotation still leaks until the `.cna` root fix (separate plan); the strip mitigates it meanwhile.
